定位

面向开发者的 CLI Agent 学习项目，深入理解模型调用、工具执行、上下文管理、多 Agent 协作、权限控制和终端交互。

核心理念：不是"一问一答"的聊天 CLI，而是持续 TUI Agent——反复请求模型、执行工具、回注结果、维护任务和上下文，并可创建后台 teammate。

项目构成

严格遵循 ReAct 框架（Reasoning + Acting）设计范式，以 Anthropic 官方 SDK 为模型接口，自研 Agent Runtime 组件体系：

Prompt 管理系统

工具系统 (17 tools)
Context 上下文管理
Hook 扩展机制
多 Agent 协作
权限与安全控制
TUI 终端交互

设计理念：模型负责推理（Reasoning），工具负责行动（Acting），循环往复直至任务收敛——每个组件围绕这一核心闭环设计。

RESEARCH QUESTION

从“会回答”到“能完成”

普通聊天模型的能力断点

模型可以给出建议，却无法自然地进入项目环境、持续执行、验证结果并处理失败。

核心问题：如何把一次回答，扩展为一个有状态、可操作、可审计的执行闭环？

01

感知环境

读取 workspace、理解上下文与任务状态，而不是脱离项目猜测。

02

采取行动

通过工具读写文件、运行命令，并把真实结果重新交给模型判断。

03

持续收敛

在权限、上下文和协作机制约束下，循环执行直至形成可验证结果。

项目定位：L1m CLI 不是另一个聊天壳，而是一套面向 Windows 终端的轻量 Agent Runtime 原型。

关键设计：AgentLoop 不直接了解 Task、Team、Permission 或 TUI——通过工具、Hook、事件回调及外部事件提供器接入，保持核心循环解耦。

明确架构债务

app.py 与 tui/shell.py 各自实现了一套：

  • 事件处理逻辑
  • token 记录与统计
  • task reminder 注入
  • context compact 装配

其他架构要点

  • TUI 监听 Agent 事件 → 映射为面板、状态文字和文件变更预览

  • AgentTeam 为每个子Agent创建独立 ContextManager
  • 所有 Agent 共享同一个真实 workspace（无文件锁/冲突检测）

TOOL SYSTEM

工具系统 — 文件操作详解

01

read_file

支持单文件 path 或 files[] batch。默认最多 60,000 字符，最大 200,000。batch 最多 8 线程并行，返回顺序保持输入顺序。支持字符 offset、上限和行范围。无需权限。

不需要权限
02

write_file

输入 path + 完整 content。默认不覆盖现有文件。空内容默认拒绝（allow_empty=true 才允许）。拒绝 ?、todo、unknown 等占位路径。单文件工具，不支持 batch。

需要权限确认
03

edit_file

单项 path/old_str/new_str 或 edits[]。old_str 必须非空且在当前文件中唯一。不同文件最多 8 组并行；同文件多编辑严格按数组顺序执行。不具备事务性。

需要权限确认

安全边界

  • 文件路径解析后必须位于 workspace（resolve_inside 校验）
  • write 拒绝占位路径、空内容和默认覆盖
  • write 拒绝 ? / todo / unknown / placeholder 等占位片段
  • edit 要求 old_str 唯一匹配（防止意外修改）
  • read/write/edit 全部经过 workspace 路径校验
  • TUI 在权限决定前显示内容预览（最多 4000 字符/80 行）

TOOL SYSTEM

工具系统 — 命令执行与四级安全

run_command 参数

参数说明
command/commands[]单项或 batch（最多8条并行）
shell=False不使用 shell 执行
cwd=workspace工作目录设为 workspace
timeout默认 30s，范围 1–120s
stdout/stderr线程持续排空，原始字节 ≤128K
最终显示截断到 12,000 字符

重要边界：workspace 只决定 cwd，并不沙箱化子进程。未被正则命中的命令仍可访问 workspace 外路径、网络或系统资源。

四级安全防线

L1 — 编码安全解码顺序：UTF-8 → 系统编码 → GBK → replacement decode
L2 — 权限确认lead 的 write_file / edit_file / run_command 需要交互确认
L3 — 硬拒绝列表Permission 和工具层双重正则拦截危险命令
L4 — 危险命令正则删除/移动/格式化/关机/taskkill/注册表删除等自动拒绝

解码降级策略：UTF-8 → 系统编码(GBK) → replacement decode，确保中文 Windows 命令输出不乱码。

CONTEXT MANAGER

上下文不是越多越好，而是要始终可控

估

调用前估算

把 system prompt、历史消息、工具说明和 Schema 统一纳入请求规模估算。

校

调用后校准

使用服务端返回的真实 usage 修正近似值，让后续判断逐步贴近实际消耗。

压

达到阈值压缩

生成高密度摘要，保留最近对话与工具结果，避免长会话无限膨胀。

Token 估算公式

$$\hat{t} = \frac{\text{bytes}_{\text{UTF-8}}}{4}$$
$$r_t = (1-\alpha) \cdot r_{t-1} + \alpha \cdot \frac{\text{real}}{\text{estimated}}$$
t̂ = 预估 token 数 bytes = 消息体 UTF-8 字节数 除数 4 = 经验常数（1 token ≈ 4 字节）
r_t = 第 t 轮的校准比率 α = 平滑系数（默认 0.3） real / estimated = 服务端返回的真实比值

EMA 比率校准

每次 API 调用后，用实际消耗 / 本地估算得到本轮观测比，再与历史比率做指数移动平均：

第 1 轮 r₁ = 1.0（初始假设估算准确）
第 2 轮 实际 1200 / 估算 1000 = 1.2 → r₂ = 0.7×1.0 + 0.3×1.2 = 1.06
第 3 轮 实际 900 / 估算 1000 = 0.9 → r₃ = 0.7×1.06 + 0.3×0.9 ≈ 1.01

α 越大响应越快但越抖，α 越小越平滑但滞后。后续所有预估都乘以当前 r_t，使本地估算逐步收敛到真实值。

CONTEXT MANAGER

Context Manager — Compact 压缩算法

1把全部历史序列化为 role: content 文本
↓
2使用 compact.md 生成新的 system prompt
↓
3发起独立模型请求生成摘要
↓
4保留最近 6 条原消息
↓
5丢弃保留区开头没有对应 tool_use 的孤立 tool_result
↓
6写成 [Context Summary] + safe tail

触发条件

当前 context tokens 或消息估算达到阈值（默认 850,000）时触发压缩。

已知精度边界

  • 本地无 DeepSeek tokenizer，核心估算为 UTF-8 字节/4
  • streaming 只统计 text delta，不覆盖 thinking/tool_use
  • compact 自身模型 usage 不进入回合 token tracker
  • app.py 非 TUI 路径没有调用 prepare_request()
  • compact_if_needed() 是始终返回 False 的占位方法

关键设计：compact 发生在 AgentLoop 外围回调中，不进入普通 usage 事件统计。压缩后的历史 = 摘要 + 最近 6 条消息的"安全尾部"，确保模型不丢失最近的对话上下文。

MULTI-AGENT

多Agent协作 — MessageBus 与当前局限

MessageBus 设计

  • 使用锁保护 mailbox，线程安全
  • 消息含：发送者、接收者、类型、request_id、metadata、状态、时间
  • 读取后状态从 unread → delivered
  • 子Agent 结果截断到 2000 字符进入 lead 上下文
  • Lead 可自动注入 inbox、team_check_inbox 或 team_wait_for_inbox

计划审批协议

waiting_plan → waiting_review → approved / rejected

不是硬性执行门禁——没有 pre-tool Hook 检查 plan 状态。是否等待批准主要依赖 sub_agent.md 提示词。

当前局限（7项）

1所有 Agent 共享同一 workspace，无文件锁/路径所有权/冲突检测
2子Agent 没有 PermissionManager——写入、编辑和命令不询问用户
3后台线程为 daemon，主进程退出会直接终止未完成工作
4没有 cancel / shutdown / join 生命周期协议
5_active 只记录名称和角色，不能表达 idle / failed / cancelled
6异常会作为 error 消息发给 lead，但没有自动重试
7inbox 消息最多 2000 字符进入上下文，长结果可能丢失证据

4 个工具

工具功能

task_list返回简化面板
task_get返回说明、依赖、active form、notes 等详情

  • 依赖不驱动调度，也不禁止提前完成

运行时行为

  • 有开放任务时，每 4 次模型调用追加一条 [Task Reminder]（仅上下文提醒，不自动更新状态）
  • 每轮完成后，若所有任务都 completed → clear_if_complete() 清空整个面板
  • 面板完成后被清空，最终验收不能机械依赖任务状态
  • 模型可以错误标记 completed / 任务可能漏拆 / 依赖不强制
